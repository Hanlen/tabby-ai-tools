# 任务流程与操作偏好

仅以 `/remember 任务描述` 开始的任务会录制。插件执行任务，记录提交的 Shell 命令与结果核对；回合和 Goal 均完成后保存流程，并提示是否设置别名。普通任务不自动固化，不按相似请求自动匹配，也没有“不检索记忆”复选框。

## 录制与使用

1. 输入 `/remember 构建前端项目并核对产物`，明确开始一个新任务。
2. 成功完成后，在提示中输入 `task1` 并点击 **保存别名**；也可以直接告诉助手“设置别名为 pm1”，或暂不设置，在设置页补充。
3. 下次直接发送 `/task1`，Codex 或 API 后端执行对应流程。已有流程可在 **设置 → AI Tools → 任务流程与偏好** 编辑别名、任务描述和步骤，或停用、删除。
4. `/workflows` 查看当前工作目录的流程，**填入任务** 填入别名，发送后执行。无别名的旧流程会填入 `/remember 任务描述`，供重新录制。

别名按工作目录隔离，不区分大小写，可输入开头的 `/`。以英文字母开头，支持字母、数字、下划线和短横线，最多 48 字符；同目录不能重复，不能覆盖 `/model`、`/remember` 等内置命令。不支持在别名后追加参数；需更改步骤或目标时先在设置页编辑。手动编辑的流程不会被后续录制覆盖。

## 查询归档状态与保存别名

助手可调用 `tabby_tabs.workflow_status()`，区分 `recording`（录制中）、`executing_alias`（执行已有流程）、`archiving`（写盘中）、`archived`（已归档）、`archive_failed`（写盘失败）、`unavailable`（录制无法归档）、`idle`（无录制记录）和 `disabled`（功能停用）。返回最近显式录制的目标、工作目录、已验收／待验收步骤、归档资格及原因；已归档时还返回流程 ID、别名和启用状态，不返回原始终端输出。

用户要求“设置别名为 pm1”时，助手先核对状态中的目标确实是用户所指流程，再调用 `workflow_set_alias(alias="pm1",workflowId=返回的流程ID)`。成功响应必须包含 `saved=true` 和回读的 `workflow.alias="pm1"`。同目录重名、内置命令名、错误流程 ID、其他会话／目录或未完成录制会被拒绝；只读模式不能修改别名。不会修改另一条旧流程来冒充完成。

checkpoint 成功只证明目标绑定或步骤验收成功，不保证录制可归档。stdin、按键和进程接管现在保存为步骤内的交互意图与处理策略，不再因为存在交互就拒绝固化。敏感命令、超过 1200 字符的命令、超过 24 步或单步超过 12 条验证命令等情况仍会标记录制不完整，状态查询与完成提示会给出原因。普通任务不能事后补存，也不要为补存重跑已完成操作；后续新任务可用 `/remember` 开始录制。

临时写盘失败会保留完整的已验收录制，`workflow_set_alias` 可直接重试归档并保存别名（尚无 ID 时省略 `workflowId`），不会重新执行终端命令。新目标发送前等待尚在完成的归档，避免丢失上一任务记录。最近完成录制的别名重试缓冲仍只在当前进程／会话中保留；执行中的流程另存最小续接记录，恢复时必须重新绑定目标并读取现场。已落盘流程在重启后仍可通过设置页管理。

## 服务器身份、路径与步骤验收

采用“结构化流程 + 内置 skill + 每次调用的隐藏提示 + 工具门禁”。具体服务器和路径保存在本地流程文件，不写进通用 skill；skill 说明如何核实身份、执行和验收，隐藏提示只携带当前调用的流程、顺序和约束。

每个步骤记录：

- `server.profileId`：Tabby 持久连接配置 ID；`server.serverId`：持久服务器标识，默认使用连接 ID，可通过实际观察绑定机器 ID。临时 tab ID 不作为服务器身份保存。
- `server.host`、`server.ip`、`server.port`、`server.username`：连接目标、已确认 IP、端口和账户。配置使用主机名时不会假造 IP，需在当前环境探测确认；连接配置不证明跳板、嵌套 SSH 或容器中的实际身份。
- `server.cwd`：步骤的绝对操作路径；本地会话目录 `workflow.cwd` 仅用于查找别名，不能替代每台服务器的操作路径。`cd`、容器切换等环境变化必须重新核实。
- `dependsOn`：前置步骤号；当前使用串行链，步骤 2 依赖步骤 1，跨服务器也按同一顺序执行。
- `verification.criteria`、`verification.evidence`、`confirmedAt`：验收条件、本次观察的简短证据及确认时间；`verificationCommands` 单独记录健康检查、产物检查等验证命令。

例如先在数据库服务器 `10.0.0.10`、连接 `ssh-db`、`/srv/database` 完成迁移并确认版本，再在应用服务器 `10.0.0.20`、连接 `ssh-app`、`/srv/application` 重启应用并检查健康端点。两台服务器执行相同命令也分别保留，不合并去重。

录制与别名执行中，模型按以下协议使用 `tabby_tabs.workflow_checkpoint`：

1. 用 `list_tabs`、`read_tab`、`get_profile` 取得当前终端和连接资料。`read_tab` 返回结构化服务器信息、当前路径和可用的 Shell 运行状态；不会返回完整凭据配置。
2. 字段缺失或存在嵌套环境时，先发送身份／路径探测命令（`send_input(verificationFor=0)`），读取结果，然后 `workflow_checkpoint(action=bind_target,tabId,target,evidence)` 绑定真实目标。身份探测只能在尚无未验收步骤时执行，不推进步骤序号。
3. 提交一个逻辑操作后，读取**同一执行终端**的新结果。额外验证命令使用 `verificationFor=当前步骤号`，在同一终端执行、单独记录，然后再次读取结果。
4. 确认命令结束且满足验收条件，调用 `workflow_checkpoint(action=confirm_step,step,tabId,criteria,evidence)`。插件拒绝缺失新观察、读取其他终端、仍在运行、没有证据或错误目标的确认；别名执行沿用已保存的验收条件。
5. 只有成功确认后，下一操作才能提交；发送中的命令也会阻止并行提交下一步。别名执行还会校验下一步的已绑定服务器和操作路径。失败或证据不足时停住依赖链，不用延时或 `sent=true` 当作成功。

没有独立机器验收策略时，由模型根据实际结果做验收，不要求用户逐步点击确认；需要额外授权或必要决策时仍会询问。未完成全部步骤验收时，即使模型标记 Goal 完成，面板仍提示继续验收，不显示为已完成流程。新录制只有全部步骤具备身份、路径和确认记录才保存。

工具门禁检查调用顺序、身份字段和新观察，业务验收默认由模型判断；配置机器验收时使用显式条件，不是通用的 Shell 退出码审计。验证命令和身份探测的用途也依赖模型遵守协议；不能把依赖步骤隐藏在一个长脚本、stdin 或标记为检查的命令中。旧流程可以读取，但缺少的身份和验收条件需现场补充，建议用 `/remember` 重新录制以持久保存。修改服务器、路径、逻辑步骤或验收条件时应重新录制；仅编辑自由文字不会重写结构化步骤。

## 条件与交互流程

`/remember` 可以记录 Shell 命令、进程接管、stdin、按键和侧栏结构化提问。模板保存目标意图和回答策略，不保存原始输入历史、密码、临时 tab ID 或完整终端输出。普通任务仍不录制，也不能事后从聊天总结生成可执行流程。

交互优先按保存的条件规则处理；规则无法确定时，使用**本次执行连接**的辅助模型；辅助模型无法处理时交回主模型当前节点。需要秘密信息或额外授权的节点保存为 `manual`，等待用户处理后继续，不必放弃整个流程。发送回答后重新读取现场，逻辑步骤仍需验收。程序身份无法确认、全屏菜单无法可靠解析或问题已经变化时，交回主模型处理。

在 **设置 → AI Tools → 任务流程与偏好 → 交互辅助模型** 为每个连接填写实际支持的模型 ID 和推理强度。留空使用当前主模型进行局部判断；不会切换主会话模型、认证或端点，也不会根据模型名字猜测速度/价格。默认单次超时 15 秒，同一节点同一观察最多两次辅助请求，每次流程最多 32 次；用量计入同一个 Goal 预算。没有进行额外的真实模型烟测；第一次实际返回也会进行结构与有效性检查。侧栏提问只有与保存问题匹配且不含秘密信息时才自动辅助回答；新的必要决策仍显示给用户。

模型工具入口：

- `workflow_configure(step, policy)`：给当前录制中已经发生的步骤保存策略。不能凭空添加已执行命令；自动验收命令必须是该步骤已运行过的验证命令。
- `workflow_run(tabId)`：推进已保存别名的条件、命令、交互和机器验收。每次调用工作量有界，后续调用从当前步骤继续。跨服务器时返回下一目标，重新绑定后继续。
- `workflow_interact(tabId, interactionId?)`：处理当前待验收步骤的一次交互，随后读回结果。
- `workflow_checkpoint(action=resolve_action,tabId,outcome=sent|not_sent,evidence)`：动作结果未知时，在读回现场后由主模型核对；不会自动重发。

`policy.when` 是 AND 条件，真时执行该步骤，假时标记 `skipped` 并继续。顺序互补的条件步骤可以表达 if/else；跳过的步骤不计为成功。条件只能读取当前 `prompt`（最后一条非空行）、`screen`（末尾最多 4000 字符）或 `commandState`，运算为 `equals`、`contains`、`not_contains`；没有任意表达式执行。优先使用精确问题和结构化状态，避免宽泛匹配旧日志。

在设置中编辑 **条件与交互策略（高级）**，JSON 对象的键是步骤编号。也可在录制时让模型通过工具配置，例如：

```json
{
  "1": {
    "interactions": [
      {
        "id": "interaction-1",
        "intent": "按用户要求保留现有配置，然后继续安装",
        "mode": "model",
        "observed": true,
        "rules": [
          {
            "when": [{ "source": "prompt", "op": "equals", "value": "Keep existing configuration? [y/n]" }],
            "response": { "kind": "answer", "text": "y" }
          }
        ]
      }
    ]
  }
}
```

规则中的回答是明确的处理策略，不从原始输入历史自动复制。菜单按当前标签和高亮处理，禁止重放历史方向键序列。模型只返回一个回答/按键、等待、升级或人工处理决策；没有终端写工具。宿主核对观察指纹、进程、所有权和有效动作后才发送。

`policy.verify` 可引用已录制的独立验证命令及 `expect` 条件，实现固定步骤的本地推进。自动验收要求可靠 Shell 完成状态，以及本次验证新增输出满足明确的正向内容条件；仅有 Shell 提示符、旧成功文本或命令回显不通过。没有机器验收规则时返回 `awaiting_verification`，主模型按原 criteria 验收。这里没有提供任意 DAG 编辑器或通用 TUI 解析器。

`workflow_status` 返回 `lifecycle`、`automation`、`skippedSteps`、`unobservedBranches` 和 `helperTokens` 等补充信息。未实际走过的交互节点保留未验证标记，不能将一次运行视为所有分支均已验证。

流程库写入升级为 v2，继续读取 v1 的串行流程。执行状态保存在同目录 `runs/`，仅保存最小脱敏状态及未知动作标记；恢复后不沿用旧 tab ID 或旧日志。**继续**会恢复当前会话的执行记录，先读取并重新绑定实际服务器、路径和进程，再验收或续接；已发送的步骤不会自动重放。已丢失的旧版录制无法凭空恢复。停止会取消辅助决策和等待；已提交的终端进程可能仍在运行。

## sudo 预检与保活

调用别名时检查已保存的命令和步骤是否包含 `sudo`。发现后，模型先核对实际执行终端、主机和目录，提前提示用户在每个执行终端运行 `sudo -v` 或 `sudo ls` 并等待确认。认证可能按 TTY 隔离，不能假定在任意终端认证即可共享。不要将密码输入对话框。

该流程的终端命令在实际 Shell 中先运行 `sudo -n -v`；失败则不执行该条命令，提示重新认证。首次成功后启动同终端的后台刷新，每 30 秒执行非交互 `sudo -n -v`，在等待下一步期间也保持认证。不会更改 sudoers 或系统超时策略。

回合结束、停止、切换或销毁时请求清理保活标记；终端空闲时清理，仍有前台进程时等待 Shell 提示符，避免将清理文字送入程序。远端缺少 Shell 集成且无法证明空闲时，无法保证立即清理；后台在原 Shell 退出、认证失败或最长 12 小时后自行终止。sudo 缓存随后按系统原有策略过期。此功能适用于支持 POSIX Shell、`sudo`、`mktemp` 的本机或 SSH 终端；系统策略禁止非交互续期时必须重新认证，不能保证绕过系统强制过期。

检查基于保存的文本；脚本内部才调用 sudo 等动态权限需求可能无法预先发现，需用户补充到流程步骤中。任务执行仍遵守现有权限；终端接管自动完成，无需人工确认。

## 存储与边界

流程库在 Tabby 配置文件同级的 `tabby-agent-memory/task-memory.json`，采用原子替换和文件锁，最多 200 条流程、100 条偏好。旧流程保留，添加别名后即可调用。偏好在设置页管理，不再使用 `/remember` 保存偏好。

只保存脱敏后的任务、步骤、目标终端标题、服务器身份与操作路径、步骤依赖、条件与交互策略、脱敏验收摘要、简短结论和次数；不保存终端原始输出、临时 tab ID、密码或原始 stdin／按键历史。交互不会单独阻止归档；敏感命令、过长或未核对的步骤仍不能作为成功流程归档。续接使用完整的最小执行记录，不将普通任务尾段拼成流程。录制和别名解析本身不调用额外模型；不确定交互的辅助决策使用当前连接并计入预算。

调用流程后仍需重新读取当前终端、核对主机、目录、分支与参数，不能直接重放历史工具调用。流程成功记录不等于每条命令的退出码均已验证。自动化测试使用模拟后端、临时目录和假 sudo，不请求模型、不使用真实 sudo 凭据。

## 限流、中断与恢复

执行中不再自动转发终端回显，模型需用 `read_tab` 主动读取结果。用户发送／继续时的有界终端摘要不能替代同终端的新观察及 `workflow_checkpoint` 验收。

后台返回 429 且 `willRetry=true` 时，面板保持等待，显示后台明确提供的下次重试时间；未提供时如实说明，不把账号额度重置时间当作重试时间。回显继续合并在本地有界缓冲区，不追加模型消息。可点击停止取消回合；这不代表终端命令已停止，模型没有继续也不代表命令仍在执行。

继续当前目标时保留已确认步骤和 `pendingStep`。先重新读取待验收步骤的实际终端，核对服务器、目录、产物及当前 Git 状态；如果命令已经完成，按原验收条件提交 `confirm_step`，再进行后续依赖。不因模型限流或缺少 checkpoint 而重复运行 stash、restore、apply 或整段历史。插件重启或切换会话后，内存中的录制进度可能不存在；应依实际状态重新核对，不自动重建或重放。
