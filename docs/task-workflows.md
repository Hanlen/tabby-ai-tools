# 任务流程与操作偏好

仅以 `/remember 任务描述` 开始的任务会录制。插件执行任务，记录提交的 Shell 命令与结果核对；回合和 Goal 均完成后保存流程，并提示是否设置别名。普通任务不自动固化，不按相似请求自动匹配，也没有“不检索记忆”复选框。

## 录制与使用

1. 输入 `/remember 构建前端项目并核对产物`，明确开始一个新任务。
2. 成功完成后，在提示中输入 `task1` 并点击 **保存别名**；也可以暂不设置，在设置页补充。
3. 下次直接发送 `/task1`，Codex 或 API 后端执行对应流程。已有流程可在 **设置 → AI Tools → 任务流程与偏好** 编辑别名、任务描述和步骤，或停用、删除。
4. `/workflows` 查看当前工作目录的流程，**填入任务** 填入别名，发送后执行。无别名的旧流程会填入 `/remember 任务描述`，供重新录制。

别名按工作目录隔离，不区分大小写，可输入开头的 `/`。以英文字母开头，支持字母、数字、下划线和短横线，最多 48 字符；同目录不能重复，不能覆盖 `/model`、`/remember` 等内置命令。不支持在别名后追加参数；需更改步骤或目标时先在设置页编辑。手动编辑的流程不会被后续录制覆盖。

## 服务器身份、路径与步骤验收

采用“结构化流程 + 内置 skill + 每次调用的隐藏提示 + 工具门禁”。具体服务器和路径保存在本地流程文件，不写进通用 skill；skill 说明如何核实身份、执行和验收，隐藏提示只携带当前调用的流程、顺序和约束。

每个步骤记录：

- `server.profileId`：Tabby 持久连接配置 ID；`server.serverId`：持久服务器标识，默认使用连接 ID，可通过实际观察绑定机器 ID。临时 tab ID 不作为服务器身份保存。
- `server.host`、`server.ip`、`server.port`、`server.username`：连接目标、已确认 IP、端口和账户。配置使用主机名时不会假造 IP，需在当前环境探测确认；连接配置不证明跳板、嵌套 SSH 或容器中的实际身份。
- `server.cwd`：步骤的绝对操作路径；本地会话目录 `workflow.cwd` 仅用于查找别名，不能替代每台服务器的操作路径。`cd`、容器切换等环境变化必须重新核实。
- `dependsOn`：前置步骤号；当前使用串行链，步骤 2 依赖步骤 1，跨服务器也按同一顺序执行。
- `verification.criteria`、`verification.evidence`、`confirmedAt`：验收条件、本次观察的简短证据及确认时间；`verificationCommands` 单独记录健康检查、产物检查等验证命令。

例如先在数据库服务器 `10.0.0.10`、连接 `ssh-db`、`/srv/database` 完成迁移并确认版本，再在应用服务器 `10.0.0.20`、连接 `ssh-app`、`/srv/application` 重启应用并检查健康端点。两台服务器执行相同命令也分别保留，不合并去重。

录制与别名执行中，模型按以下协议使用 `tabby_tabs.workflow_checkpoint`：

1. 用 `list_tabs`、`read_tab`、`get_profile` 取得当前终端和连接资料。`read_tab` 返回结构化服务器信息、当前路径和可用的 Shell 运行状态；不会返回完整凭据配置。
2. 字段缺失或存在嵌套环境时，先发送身份／路径探测命令（`send_input(verificationFor=0)`），读取结果，然后 `workflow_checkpoint(action=bind_target,tabId,target,evidence)` 绑定真实目标。身份探测只能在尚无未验收步骤时执行，不推进步骤序号。
3. 提交一个逻辑操作后，读取**同一执行终端**的新结果。额外验证命令使用 `verificationFor=当前步骤号`，在同一终端执行、单独记录，然后再次读取结果。
4. 确认命令结束且满足验收条件，调用 `workflow_checkpoint(action=confirm_step,step,tabId,criteria,evidence)`。插件拒绝缺失新观察、读取其他终端、仍在运行、没有证据或错误目标的确认；别名执行沿用已保存的验收条件。
5. 只有成功确认后，下一操作才能提交；发送中的命令也会阻止并行提交下一步。别名执行还会校验下一步的已绑定服务器和操作路径。失败或证据不足时停住依赖链，不用延时或 `sent=true` 当作成功。

这里的确认是模型根据实际结果做验收，不要求用户逐步点击确认；需要额外授权或必要决策时仍会询问。未完成全部步骤验收时，即使模型标记 Goal 完成，面板仍提示继续验收，不显示为已完成流程。新录制只有全部步骤具备身份、路径和确认记录才保存。

工具门禁检查调用顺序、身份字段和新观察，业务验收是否成立仍由模型判断，不是独立的 Shell 退出码审计。验证命令和身份探测的用途也依赖模型遵守协议；不能把依赖步骤隐藏在一个长脚本、stdin 或标记为检查的命令中。旧流程可以读取，但缺少的身份和验收条件需现场补充，建议用 `/remember` 重新录制以持久保存。修改服务器、路径、逻辑步骤或验收条件时应重新录制；仅编辑自由文字不会重写结构化步骤。

## sudo 预检与保活

调用别名时检查已保存的命令和步骤是否包含 `sudo`。发现后，模型先核对实际执行终端、主机和目录，提前提示用户在每个执行终端运行 `sudo -v` 或 `sudo ls` 并等待确认。认证可能按 TTY 隔离，不能假定在任意终端认证即可共享。不要将密码输入对话框。

该流程的终端命令在实际 Shell 中先运行 `sudo -n -v`；失败则不执行该条命令，提示重新认证。首次成功后启动同终端的后台刷新，每 30 秒执行非交互 `sudo -n -v`，在等待下一步期间也保持认证。不会更改 sudoers 或系统超时策略。

回合结束、停止、切换或销毁时请求清理保活标记；终端空闲时清理，仍有前台进程时等待 Shell 提示符，避免将清理文字送入程序。远端缺少 Shell 集成且无法证明空闲时，无法保证立即清理；后台在原 Shell 退出、认证失败或最长 12 小时后自行终止。sudo 缓存随后按系统原有策略过期。此功能适用于支持 POSIX Shell、`sudo`、`mktemp` 的本机或 SSH 终端；系统策略禁止非交互续期时必须重新认证，不能保证绕过系统强制过期。

检查基于保存的文本；脚本内部才调用 sudo 等动态权限需求可能无法预先发现，需用户补充到流程步骤中。任务执行仍遵守现有权限；终端接管自动完成，无需人工确认。

## 存储与边界

流程库在 Tabby 配置文件同级的 `tabby-agent-memory/task-memory.json`，采用原子替换和文件锁，最多 200 条流程、100 条偏好。旧流程保留，添加别名后即可调用。偏好在设置页管理，不再使用 `/remember` 保存偏好。

只保存脱敏后的任务、步骤、目标终端标题、服务器身份与操作路径、步骤依赖、脱敏验收摘要、简短结论和次数；不保存终端原始输出、临时 tab ID、密码或交互式 stdin。存在交互输入、敏感命令、过长或未核对的步骤时不归档；恢复任务的尾段不会拼成完整流程。录制和别名解析本身不调用模型；执行任务使用所选后端。

调用流程后仍需重新读取当前终端、核对主机、目录、分支与参数，不能直接重放历史工具调用。流程成功记录不等于每条命令的退出码均已验证。自动化测试使用模拟后端、临时目录和假 sudo，不请求模型、不使用真实 sudo 凭据。

## 限流、中断与恢复

执行中不再自动转发终端回显，模型需用 `read_tab` 主动读取结果。用户发送／继续时的有界终端摘要不能替代同终端的新观察及 `workflow_checkpoint` 验收。

后台返回 429 且 `willRetry=true` 时，面板保持等待，显示后台明确提供的下次重试时间；未提供时如实说明，不把账号额度重置时间当作重试时间。回显继续合并在本地有界缓冲区，不追加模型消息。可点击停止取消回合；这不代表终端命令已停止，模型没有继续也不代表命令仍在执行。

继续当前目标时保留已确认步骤和 `pendingStep`。先重新读取待验收步骤的实际终端，核对服务器、目录、产物及当前 Git 状态；如果命令已经完成，按原验收条件提交 `confirm_step`，再进行后续依赖。不因模型限流或缺少 checkpoint 而重复运行 stash、restore、apply 或整段历史。插件重启或切换会话后，内存中的录制进度可能不存在；应依实际状态重新核对，不自动重建或重放。
