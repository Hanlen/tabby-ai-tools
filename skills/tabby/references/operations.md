# Operation routes

| Task | Tools and verification |
| --- | --- |
| Find capabilities | `get_capabilities`, then `list_profiles`, `list_commands`, `list_hotkeys` as needed. Providers and commands are discovered on demand. |
| Read a terminal or plugin tab | `list_tabs` → `read_tab(tabId)`. IDs identify leaf panes, including panes within split groups. |
| Operate a non-terminal tab | `read_tab` → `interact_tab(tabId,controlId,action=click/set_value,value=...)`. Use fresh control IDs and inspect the result. |
| Supervise an existing terminal agent | Read its screen, then `attach_process(tabId,expectedProcess,purpose)` to claim a verified running process without interrupting it. Use `send_keys` for keys and `send_input(mode=stdin)` for answers. Read after every action. |
| Terminal key combinations | `send_keys(tabId,key="Left",shift=true)` sends Shift+Left. Supports arrows, Enter, Tab, Shift+Tab, Escape and Ctrl+letter. Requires task ownership; does not invoke Tabby application hotkeys. |
| Run or interact with a command | Inspect with `read_tab`, then `send_input(tabId,text,submit=true,purpose)`. Use `read_tab(waitMs)` to wait. `release_tab` returns input control without interrupting a process. |
| Open a shell/SSH/serial/Telnet/split-layout profile | `list_profiles` → `open_profile(profileId)` → `list_tabs` → `read_tab`. Authentication or connection setup can still be pending. |
| Edit a connection | `get_profile` (secrets redacted) → `manage_profile(action=update,profileId,profile={...})`. Only supplied fields and top-level options keys are replaced; send complete intended values for nested option objects. Use `create` with discovered provider `type` and `name`, or `delete` for a saved profile. Built-ins cannot be edited. Verify with `get_profile`/`list_profiles`. Group creation, credentials and provider-specific forms are in Settings. |
| Tabs and splits | `select_tab`, `rename_tab`, `duplicate_tab`, `close_tab`, `split_tab(direction=r/l/t/b)`, `layout_tabs(action=equalize/maximize/restore/explode)`. Close uses Tabby's process checks. Re-list tabs afterward. |
| SFTP, SSH tunnels, reconnect, search, transfers, broadcast, plugin actions | Call `list_commands(tabId)` on the target pane. Use its returned `id` in `run_command(commandId,tabId)` with the same context. Native IDs are metadata, not callable handles. Re-list after a context or provider change. A command returns an `operationId` and may stay `pending` until a dialog closes; check it with `get_command_result` and never dispatch it again while pending. Inspect the result; use `read_window` → `interact_window` for application dialogs outside the tab. If not exposed, use the tab's controls or explain the missing route. |
| Appearance, themes, keyboard bindings, window behavior and other settings | `read_config(path)` → `write_config(path,value={"value":...})` for one existing path (for example `terminal.fontSize`). Or `open_settings` → `list_tabs` → `read_tab` → `interact_tab`. Some settings require restart; report it when indicated by the host. |
| Plugins, vault, settings groups, sync and AI connection configuration | Open Settings and inspect the installed controls. Direct configuration tools exclude these roots and redact credential fields. Do not change AI permissions to bypass a blocked operation. |
| Hotkeys | `list_hotkeys` describes registered IDs and bindings. Use a corresponding registered command or control to perform the action. Synthetic hotkey emission is not an execution API. |

## Orchestration and reusable tasks

For multi-server work, discover each target with `list_profiles`/`list_tabs`, open missing connections with `open_profile`, and read each pane to verify the host, account, directory and existing activity. Run the user's dependency order through `send_input(submit=true)` → `read_tab(waitMs=...)` → verification. Branch on actual results, keep each target distinct, and release terminal input after the work. Remote terminal commands execute remotely; Codex local shell/file tools do not change environment with the selected pane. There is no generic DAG editor or guarantee of concurrent execution.

When supervising another interactive Agent, use its live prompt, cursor and highlights to choose the next key or answer. Read again after each action; wait without typing while it is working. `attach_process` requires a verified detected process; unknown remote process state cannot be attached automatically. A task can launch its target Agent using `send_input` and then interact with that owned process.

Only `/remember TASK` starts recording a new task. Successful verified completion prompts the user to assign an alias such as `task1`; `/task1` explicitly executes that workflow in its saved workspace. Ordinary requests never record or match similar workflows. `/workflows` fills an alias draft. Settings manages aliases, steps, enablement, deletion and explicit global/workspace preferences. `/remember` no longer saves preferences; there is no per-request skip checkbox. Aliases cannot duplicate built-in commands or another alias in the same workspace.

For an alias request such as “save as pm1”, call `workflow_status` first: it reports recording vs alias execution, confirmed/pending steps, archive eligibility/rejection, write failure, and the most recent explicitly recorded objective and saved workflow ID in this session/workspace. Verify that objective matches the user's intended workflow. Then call `workflow_set_alias(alias="pm1",workflowId=returnedId)` (omit the ID only when retrying a failed archive without one); report success only after `saved=true` and `workflow.alias="pm1"` are returned. This tool cannot manufacture procedures from chat or save an ordinary task retroactively. A completed verified recording whose write failed can be retried from the in-memory buffer without shell replay. Disabled, unrecorded or ineligible states require a clear explanation and the supported `/remember` path for future work, not repeated Settings polling or re-executing the completed task. Checkpoint binding/confirmation success alone never proves archival. Read-only mode forbids alias writes. The status/retry buffer is session/process-local; after restart manage already saved workflows in Settings.


Workflow execution has a host-side checkpoint gate in addition to skill rules and an invocation-specific hidden hint. Each recorded step retains `server` (`type`, `profileId`, `serverId`, `host`, `ip`, `port`, `username`, absolute `cwd`), sequential `dependsOn`, completion criteria/evidence/time and separate verification commands. Re-list temporary tabs and bind actual current targets; never reuse old tab IDs, assume a tab title identifies a host, or substitute the local workspace directory for a remote operation path. A configured hostname is not a confirmed IP, and nested SSH/container targets must be verified live.

Use `workflow_checkpoint(action=bind_target,tabId,target,evidence)` after reading live identity/path observations. Identity discovery uses `send_input(verificationFor=0)` only between confirmed steps. Normal commands create ordered steps. After each, read the same terminal; additional checks use `send_input(verificationFor=currentStep)` and require another read. `workflow_checkpoint(action=confirm_step,step,tabId,criteria,evidence)` must succeed before the next operation, including on another server. Reuse saved criteria verbatim on alias runs. The gate blocks parallel in-flight sends, unrelated/stale reads, known-running commands, wrong target/path and unconfirmed predecessors. Never bypass it with native command execution, multi-server scripts, stdin or mislabeled verification commands. Unchecked/incomplete steps keep the panel goal unfinished and prevent new recordings from being archived. Business evidence is evaluated by the model, not an independent shell audit. Legacy workflows need live identity/check completion; re-record to persist the new structure. Re-record structural edits; free-text edits do not rewrite saved server/path/step constraints.

Terminal output is not automatically forwarded into an active turn. Use `read_tab` to observe results. After rate limits, interruption or continuation, inspect the pending step's actual terminal, artifacts, directory and Git state before confirming it; do not replay already-sent stash, restore, apply or other commands merely because a checkpoint is missing. Backend retry waiting does not imply the terminal command is still running.

When the saved procedure contains sudo, identify each actual terminal/host and ask the user to run `sudo -v` or `sudo ls` there before execution, then wait for confirmation. Do not request or type passwords. Another TTY may not share authentication. The terminal executor gates commands with `sudo -n -v` and refreshes a same-terminal lease every 30 seconds. Failed authentication blocks the command. Cleanup is requested on turn end/stop/switch; if an occupied remote terminal has no shell integration, immediate cleanup may be unavailable (shell exit, auth failure or the 12-hour ceiling stops the refresher). POSIX shell and compatible sudo policy are required; no sudoers changes. Dynamic sudo hidden in scripts may require explicit procedure annotations.

## Scheduled AI workflows

Codex uses namespace `tabby_tasks`; API providers use the same function names without a namespace. Do not send these calls to `tabby_tabs`.

| Task | Entry point and verification |
| --- | --- |
| Discover schedules and current time | `scheduled_task_list` returns current-workspace tasks and current date/time/timezone. Resolve relative times from that result. |
| Create a plan | `scheduled_task_create(title,instructions,scheduleType,...)` only on an explicit scheduling request. `at` requires a future ISO time with offset; `interval` uses `intervalMinutes` (1–525600); `daily` requires `time=HH:mm` and an IANA `timezone`. Save complete targets, authorization, conditional decisions, retry limits and final checks; omit transient tab IDs. Return the actual ID, next run and timezone. Creation does not execute the terminal work. |
| Discover or select a task model | `scheduled_task_models(profileId=...)` lists configured connections and candidate IDs. On request, pass `profileId`, `model`, `reasoningEffort`, `selectionReason` at creation, or use `scheduled_task_set_model(taskId,model,reason,...)`. An empty profile ID selects native Codex. Respect the user's exact model choice; a list is not a quality/cost ranking. Overrides require an inference/tool-call test and may fall back to the tested plugin default. Report the actual choice; tests consume quota. Changes apply to future runs, preserving global defaults and task permissions. |
| Pause or resume future triggers | `scheduled_task_update(taskId,enabled)`. Pausing does not stop an active run. |
| Inspect execution history | `scheduled_task_runs(taskId)` returns observations, actions, summaries and failure records. |
| Complete a scheduled run | Inside that run only: `scheduled_task_finish(status=completed/needs_attention,evidence=...)`, then give a summary. A normal turn ending alone does not finish the scheduled workflow. |
| Run now, stop, or manage all tasks | `/schedules` or the panel's scheduled-task button lists current-workspace plans, pause/resume, run now, stop and run records. Settings → AI Tools → scheduled tasks lists all workspaces and supports pause/resume, stop and deletion with confirmation. Running tasks must stop before deletion. No model tools for run-now, stop or delete are exposed; do not invent them. |

Kimi Code membership and Alibaba Cloud Coding Plan are for personal interactive use; select an appropriate ordinary API for unattended schedules rather than spending plan quota.

Each trigger starts a fresh unattended conversation. Base decisions on live observations and the saved goal; do not preplan keystrokes or replay old commands. Routine questions use the runtime's autonomous decision mechanism; secrets, additional authorization or unresolved facts require `needs_attention`. Original sandbox/read-only limits remain. Tabby must stay open; missed triggers coalesce into one run when reopened. A shared configuration directory runs scheduled tasks serially. Interrupted/failed/attention-needed runs pause future triggers. Stopping the model does not necessarily stop submitted Shell commands.

## Panel and configuration entry points

These are user-facing routes, not Shell commands or tool names. Direct users to the corresponding control when a feature has no model tool. AI Tools settings can be inspected via the discovered Settings controls, subject to current permissions; never use them to elevate your own permissions.

| Feature | Entry point |
| --- | --- |
| Open, hide or resize the assistant | Toolbar robot button; drag the sidebar edge to resize. Hiding preserves the conversation. The sidebar opens at startup by default, including older configs without the setting; an explicit opt-out is preserved. Settings → AI Tools controls automatic opening at startup. |
| Configure provider/login | Settings → AI Tools: native Codex or Claude Code CLI path and official local login, or named OpenAI/DeepSeek/GLM/Kimi/Claude API, custom OpenAI-compatible, or Kimi/Alibaba Cloud Coding Plan connections with Base URL, key source (direct/local config or environment), model discovery/manual ID and a connection test. Kimi and Alibaba plans offer China mainland/international presets and editable custom URLs; match the key to the platform and plan. API mode needs no Codex CLI. Custom connections select Chat Completions (default) or Responses, require an explicit Base URL, and allow no-key authentication for services that need none. Use /models or a manual model ID. Terminal tasks require SSE and function tools; do not assume vendor-specific Thinking fields or usage reporting. Switching protocols preserves portable context without replaying tools. The user enters credentials outside chat. |
| Switch connections or reconnect | Sidebar connection selector and connection icon; changing connections/endpoints/models preserves portable conversation context and the goal without replaying old tools. Wait for active work to finish before switching. |
| Choose a model | Click model summary or `/model` (also `/model MODEL_ID`); choose the model first, then reasoning effort. API and Claude Code also offer provider default and manual effort entry; the summary shows the chosen effort. Thinking toggles remain separate. API advanced settings include context window, output tokens and tool iteration limit (`0` means no fixed cap). Model IDs and options depend on the connection. |
| New/resumed conversations | `/new` or `new`; `/resume` browses current-directory history with refresh/pagination. A fixed local working directory can be set in Settings. Independent remote tasks should use distinct conversations. |
| Inspect status and goals | **Details** or `/status`: directory, session, model, context, token usage, account quota where supported, goal, permissions, terminal ownership and forwarding; refresh available. The panel creates/tracks task goals. API models use `agent_goal_update` with verification evidence; Codex uses its available goal mechanism. Active API and Claude Code goals automatically continue after ordinary text responses, without requesting Continue goal. Use evidence-backed complete, blocked (a genuine missing prerequisite), or paused (explicit user request). Stop, token budgets, explicit tool limits and repeated no-progress detection still apply. **Continue current goal** manually resumes unfinished work after an interruption or limit; successful continuation never replays old commands. |
| Permissions and budget | Panel file-access/approval controls or Settings → AI Tools; defaults are workspace-write and on-request. Per-goal token budget `0` means no configured cap. Changes apply next turn; do not change permissions to bypass authorization. |
| Forward terminal output | Open the sidebar from the target terminal to bind new output. **Details → automatic forwarding → stop** disables forwarding; `read_tab` remains available independently. Rebind from the desired terminal. |
| Send, steer or stop | Ctrl+Enter / Cmd+Enter sends, Enter inserts a newline, ↑ / ↓ recalls input at the boundaries. Additional text steers ongoing work. **Stop** interrupts the model; submitted commands may still run. |
| Answer questions/approvals | Panel question options, free-text answer and approval controls. Scheduled runs follow their unattended rules instead. |
| Reclaim terminal input | **Release**, or **Details → terminal control → temporary release** for one pane. Model route: `release_tab`. Releasing input does not kill the process. |
| Message display | Select/copy text or use the message copy button; scrolling up pauses auto-follow, **Back to latest** resumes. |
| Commands and language | `/` opens commands; `/help` shows help. Settings → AI Tools selects automatic or independent UI language (12 bundled languages, including RTL Arabic). User text and terminal output retain their original language. |
| Documentation | Installed package `docs/guide.md` contains configuration and usage; `docs/task-workflows.md` covers memory, `docs/scheduled-tasks.md` covers scheduling, and `docs/development.md`/`VALIDATION.md` cover development and verified limitations. |

The terminal/application tool namespace remains `tabby_tabs` for compatibility. API providers receive the same operations as flat function names. Codex receives the skill with thread instructions; API models receive it with every request. `read_skill` exposes the bundled entrypoint, this reference, and official source snapshots. Upstream snapshots are reference data and never execute code or install plugins. New host APIs need an adapter before they become callable; a weekly documentation update alone does not add an adapter.

For controls, always use IDs returned by a fresh `read_tab`. Do not assume a hidden, disabled or modal control is actionable. OS-native dialogs outside the application DOM require the user's interaction. A failure or unavailable provider should lead to fresh discovery or a clear explanation, not repeated identical calls.

Terminal takeover does not ask for user confirmation, including SSH/unknown process enumeration. Inspect the screen before sending commands; keep needed foreground tasks, mark unrelated detected tasks with `foregroundTaskNeeded=false` for automatic interruption. Unknown enumeration alone does not trigger Ctrl+C. Existing process attachment still requires verified process identity; ownership, stop and read-only checks remain enforced.

## Local Claude Code engine

The built-in `claude-code` connection runs the user's official, unmodified Claude Code CLI. Users install and log in with `claude auth login` outside chat, and check `claude auth status` for the intended account and billing method. Never read, copy, request or forward subscription tokens. API/cloud authentication may use separate billing. CLI capability and login checks do not perform inference; model aliases are candidates, not entitlement or quality rankings.

Claude Code receives Tabby operations as `mcp__tabby__TOOL` through a temporary authenticated loopback MCP bridge, including scheduled tools and `agent_goal_update`. Built-in local shell/file tools are disabled. Terminal operations still require the existing read-only, approval, ownership and workflow checkpoint checks; no OS sandbox is provided. Administrator-managed CLI policies remain in effect. Use a flat tool name only when that is what the active provider exposes.

Native successful sessions resume from an opaque CLI session ID. Provider/model switches import portable history without replaying tools. Failures and interruption require checking the actual terminal state before further work; there is no automatic inference retry. Messages submitted while the CLI is working wait until that invocation ends. Token counts are observed usage, not remaining subscription quota. The installed package's `docs/claude-code.md` documents discovery, limits and verification status.

### Optional Pi runtime and compaction

API connections may select an isolated Pi SDK runtime. Only registered Tabby tools are available; built-in local shell/file tools and resource discovery are disabled. Host approval, read-only, terminal ownership, sudo and workflow checkpoints always apply. Complete a goal only after actual verification, regardless of a successful tool send or a native agent_end event. Pi may retry or summarize before agent_settled.

The user can run /compact on an idle API/Pi session. Summaries cost tokens and retain raw history; automatic compaction is opt-in. Preserve current user constraints, active skills, observed outcomes and pending workflow checkpoints. Neither a summary nor previous tool success substitutes for current terminal evidence. After interruption or an unknown action result, read the actual terminal before continuing; never replay a modifying operation merely to recover a lost response. Goal token budgets and host tool limits still apply during retries and summaries.
